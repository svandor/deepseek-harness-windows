# INCIDENT — 2026-10-15: "the auto model did not start", "Connection error", wrong footer

> Hungarian version: [`INCIDENT-2026-10-15.md`](INCIDENT-2026-10-15.md).

**Symptoms (from the user's side):**
1. in the morning the `auto` model served nothing ("the model selector did not start"),
2. a repeating **`Connection error`** (TRANSPORT) in the interface, failing after 5/5 retries,
3. the footer's Alibaba side showed the **log-estimated** value (`-$0.1254`) instead of the real
   invoice, with an "*Unexpected end of JSON input*" error.

**What actually happened — four faults stacked on top of each other.** None of them was the
model selector's fault.

| # | Cause | Evidence |
|---|---|---|
| 1 | **The proxy process (127.0.0.1:4123) stopped**, and nothing restarted it | the job ended with `exit code: 1`, its log kept working endlessly in the meantime; `healthz` did not answer; **no watchdog was running** |
| 2 | **DeepSeek peak (01–04, 06–10 UTC): the provider was overloaded** | `deepseek-flash → HTTP 503: "Service is too busy. We advise users to temporarily switch to alternative LLM API service providers."`; the `deepseek-v4-pro` streams broke |
| 3 | **The escalation chain contained only DeepSeek targets** | `eszkalacio-porgas -> deepseek-v4-pro -> deepseek-flash`, and when both fell, the request had nowhere to go; each attempt stalled for **~5 minutes** (stall/connect timeout) |
| 4 | **The running `dsh web` process was older than the plugin change**, so `GET /ui-extras/alibaba` returned **404** (empty body → the client printed a JSON error) | the plugin's `index.js` was modified at 18:12, the PID serving 3080 **started at 17:18**; `state\restart.log` **did not exist** → the restart helper never ran |

**A misleading trace:** there are two plugin copies on the machine —
`plugins\dsh-ui-extras\lib\index.js` (the one we edit) and
`dist\stage\plugins\dsh-ui-extras\lib\index.js` (install staging, **dated 2026-10-02**).
The running server served the old code, which is why it looked like "the code does not even
contain" the route.

## What we fixed (permanently)

1. **Escalation chain:**
   `eszkalacio-porgas -> deepseek/deepseek-v4-pro -> deepseek/deepseek-flash -> alibaba-intl/qwen3.7-flash -> alibaba/qwen3.7-flash`.
   A DeepSeek outage thus **cannot take the request away**, because the working (free) Alibaba
   target is always at the end.
2. **Faster handover:** `stallTimeoutMs` 180 s → **90 s**, the DeepSeek target's `connectTimeoutMs`
   **45 s**. A stuck attempt now hands over in seconds instead of waiting 5 minutes.
3. **Launcher-independent resolution:** the proxy resolves the endpoints **and** the keys directly
   from `~/.dsh/.credentials.yaml` (`credentialRef`), together with the required-key gate.
   It starts without environment variables — the watchdog/launcher cannot start it "empty".
4. **Watchdog:** `providers\start-watchdog.cmd` → `start-watchdog-hidden.vbs`. Without the watchdog
   running, the proxy's death goes unnoticed. **Task Scheduler refused the logon registration**, so
   it has to be done once by hand:
   `schtasks /Create /TN DSH-ProxyWatchdog /TR "\"C:\Szerver\Deepseek Harness\providers\start-watchdog.cmd\"" /SC ONLOGON /F`

## How to diagnose this (in this order!)

1. **Is the proxy alive?** `curl http://127.0.0.1:4123/healthz` → `ok`, `usable`, `missingKeys`.
   Do *not* rely on `Get-NetTCPConnection`: without admin it returns an empty list and looks like
   "no listener".
2. **The proxy's log:** if it was started as a background job, the log is in the **job's output**,
   not in `proxy.out.log` (only the `run-proxy-service.ps1` path writes to the file).
3. **The running harness's plugin version:** `GET /ui-extras/balance` and `GET /ui-extras/alibaba`.
   If `balance` is 200 and `alibaba` is **404**, the running process is **older than the plugin file**.
4. **File vs. process:** compare the plugin `index.js` modification time with the start time of the
   `dsh web` PID (`Get-Process node | Select Id,StartTime`).
5. **Several plugin copies:** `Get-ChildItem C:\ -Recurse -Filter index.js | Where-Object { $_.FullName -match 'dsh-ui-extras\\lib\\index\.js$' }`.
   `dist\stage\...` is **install staging** and may be older — do not diagnose from it.
6. **Did the restart really happen?** The helper writes to `state\restart.log`. If that file is
   missing, **no helper ran** — the interface merely reloaded (which does not start a new server).
7. The `auto` decisions are readable in the proxy log:
   `AUTO auto: VALASZTAS …` / `AUTO auto: RAGADOS …` / `AUTO auto: eszkalacio-porgas …`.

## Restarting the harness (the right way)

The plugin's **own helper** (`plugins/dsh-ui-extras/restart-node.js`) is the only safe route: it runs
detached, kills the process listening on 3080, starts a fresh `dsh web`, and writes the new token URL
into `state/harness.url` (the interface reloads itself from that).

**Do NOT** restart the harness from the session you are working in — when the server stops, the
browser's transport breaks, and that is exactly the `Connection error` we saw.

Manual start (through a **`.cmd` shim**, because of the 261-character `/TR` limit and the process-tree
kill, with Task Scheduler):
`providers\restart-harness.cmd` (calls the helper with a 4 s delay), then
`schtasks /Run /TN DSH-RestartHarness`.

## Windows/PowerShell traps (these hurt too)

- **PowerShell 5.1:** there is no `??`, and `if` cannot be used as an expression after `+` → separate statement.
- **`$home` is a reserved variable** (automatic) → use `$dshHome`.
- **`schtasks /TR` ≤ 261 characters** → a `.cmd` shim is needed (the repo's retune scripts do it for the same reason).
- **The pwsh tool kills the process tree**, so a server started with `Start-Process` dies; for a durable
  start use Task Scheduler or the project watchdog.
- **`filter-branch` uses `sh`** (named pipes) → in the sandbox it needs escalation; give `sh` a
  **forward-slash** path (`C:/...`), otherwise it swallows the backslashes.
- **`git push`** from the sandbox dies with `SEC_E_NO_CREDENTIALS` → with escalation it works.
